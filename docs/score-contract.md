# Question-score contract v1 / 질문 점수 정본 계약

This is a DevEval operational data contract, not an additional KOICA scoring
rule. Question judgments remain provisional and evidence-based. Formula and
grade boundaries follow the existing normative digest §2/§2-1.

## Files and authority

- `ratings/<criterion>.md`: each isolated evaluator's response, ending with
  one `json` fenced object for that criterion. The parent saves it unchanged.
- `ratings.json`: collected pre-verification question judgments; no aggregate
  fields are allowed. `score_calculate.py collect` adds project/source metadata.
- `verified-scores.json`: the verifier's corrected full input object, saved by
  the lead. It preserves project/source identity and includes all five criteria.
- `score-result.json`: derived values; editing this file cannot change the
  authoritative input or make a mismatched report pass.
- `auditable-evaluation-brief.md`: summary and criterion question-score blocks
  are generated by code and rechecked against the input JSON.

The template is `templates/score-input-template.json`. Its `pending` statuses
are intentionally invalid: complete every question before calculating.

## Input schema

Root fields: `schema_version: 1`, nonempty `project`, the converted source's
64-character lowercase `source_sha256`, `profile`, `verification`, and
`criteria`. Unknown fields, duplicate JSON keys, NaN and Infinity are rejected.

`profile` is `koica-2024` by default: relevance 2 questions, coherence 2,
effectiveness 3, efficiency 2, sustainability 2. `koica-legacy-weighted`
supports the cited older weighted form with a third relevance question.
Choose that profile only from the applicable form, with its weights and source.
Other question sets need an explicit contract extension; never drop a question
to make an input fit. Impact remains outside the 20-point composite.

Each criterion has `criterion` (the five English IDs above), `questions`, and
optional `aggregation`, `weight_basis`, `summary`, and `conflict_ids`. Inputs
with `verification: not_reviewed` may retain their own local candidate IDs
(REL-Xn/COH-Xn/EFF-Xn/EFI-Xn/SUS-Xn). Verified inputs allow only global `X1`, …
IDs, and the final audit requires every listed ID to exist in the register.
Omitting `conflict_ids` means unreported, not "no conflicts": the generated
table marks it for confirmation and the computation is conditional. Use `[]`
only when the verifier actually confirms that no conflict applies.
`aggregation` is `mean` or `weighted_mean`. Weighted means require a cited
`weight_basis` and a positive `weight` on every question, with sum exactly 1.

Every question has:

| Field | Contract |
|---|---|
| `id` | `q1`, `q2`, and `q3` where applicable; none missing or duplicated |
| `status` | `scored`, `unavailable`, or `not_applicable` |
| `score` | Number from 1 to 4 in 0.5 steps when scored; otherwise `null` |
| `fact_ids` | Unique `F1`, … references; at least one for a scored question |
| `reason` | Nonempty evidence-based judgment or reason for exclusion |
| `weight` | Present only for weighted means; positive, at most 6 decimal places |

Root `verification` is `not_reviewed`, `passed`, `conditional`, or `rejected`.
Final report projection accepts only `passed`/`conditional`. Excluded questions
force a conditional computation even when the input says passed.

Optional root `scenarios` is a list (maximum 20) with unique `S1`, … IDs,
`reason`, and `changes`. Each change has `criterion`, `question` (`q1`, …),
`score`, `fact_ids`, and `reason`. It replaces that question's judgment for the
scenario; the code recalculates the total, grade, and min/max across the base
and scenarios. The model supplies evidence-backed alternative question scores,
never a hand-calculated total/range. Unknown or duplicate question changes fail.

## Arithmetic and exclusions

Unscored questions are excluded, never converted to zero. Remaining weights
are renormalized. With no scorable question, that criterion is unavailable;
with any unavailable criterion, the composite and grade are withheld. Round
each criterion to two decimal places with Decimal `ROUND_HALF_UP`, then add
the five criterion scores. Grades are A ≥18, B ≥16, C ≥14, D ≥12, E ≥10, F <10.
The code does not decide whether evidence warrants a question's assigned score.

## Commands (use absolute script paths from outside the plugin)

```sh
python3 scripts/score_calculate.py collect --directory /work/.omo/project/ratings --manifest /work/.omo/project/delegation-manifest.json --project project --out /work/.omo/project/ratings.json
python3 scripts/score_calculate.py calculate --input /work/.omo/project/ratings.json --out /work/.omo/project/pre-score-result.json
python3 scripts/score_calculate.py render --input /work/.omo/project/verified-scores.json --before /work/.omo/project/ratings.json --brief /work/.omo/project/auditable-evaluation-brief.md --out /work/.omo/project/score-result.json
python3 scripts/auditable_output_check.py /work/.omo/project/auditable-evaluation-brief.md --require-scores --require-isolation
```

The scorer writes section 3 and marked question-score blocks in section 4.
The composer writes evidence, counterevidence, corrections and recommendations;
it must not hand-calculate or edit generated scores. Sensitivity assumptions
remain explicit; use structured scenarios for a numeric interval and never
invent its aggregate bounds.

For a full report, `score_calculate.py export --input … --before … --out
score-tables.md` generates the same blocks. Include their binding and contents
verbatim in the report, keeping the JSON files in the same project folder, and
run `score_calculate.py check --input … --before … --brief draft-report.md`.
The free-form numeric checker remains useful for other narrative claims and
externally authored reports; it does not replace the strict authored-output gate.

## Isolation evidence

`delegation_check.py prepare` freezes sections 1–2 as `source-pack.md` and binds
the packet, converted source and index hashes in `delegation-manifest.json`.
Pass both printed SHA markers and the packet's absolute path to every criterion.
Codex uses the exact generated `task_names` values (criterion plus an input-hash
scope) and `fork_turns: "none"`; Claude must use fresh registered evaluators,
foreground calls, and no resume. The native JSONL trace is checked; a self-written
"independent" assertion is not evidence. `isolation.json` is rechecked against
the trace at final audit. Unsupported/missing trace evidence returns exit 3.

This verifies parent-history separation and the declared frozen input scope, not filesystem
sandboxing, blind removal of the original human report's grade, or scoring
accuracy. Claude's separate context behavior is documented in its
[official subagent documentation](https://code.claude.com/docs/en/sub-agents).

Some Codex logs redact the delegation body. In that format, the checker uses
the clear task-scope hash, `fork_turns`, successful calls and frozen-file hashes.
It sets `prompt_bodies_verified: false` and preserves a limitation: the exact
explicit prompt body was not inspected. It never decrypts protected log fields
or treats an absent/redacted body as proof that no extra data was supplied.
